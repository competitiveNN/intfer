## 2. What it changes and the mechanism

`quant_gemm_dpas48` runs **one WI per (row `m`, 16-N tile `t`)** and, inside its
K loop, recomputes the activation column sums:

```
S  = sum_{k<32} va[k]                 (u4 / u8 / u2 non-split)
S0 = sum_{k<16} va[k], Sf = S - S0    (INT2/G16 linearity split)
```

Those depend **only on (row, op)** — never on the tile. So each of the
`nT = N/16` tiles per row recomputes an identical **O(K) integer fold**. That
replication is the documented reason the wide-N DPAS kernel loses to the legacy
tiled path even though the multiply itself is on XMX.

This flag adds `quant_gemm_dpas48_rowfold`, a small plain-SYCL kernel that
computes those sums **once per (row, op)** into a grow-only per-device
workspace (`2 * M * nOp` INT32 — tiny, `K/32` entries). The DPAS kernel then
just reads them. It dep-chains on the existing pre-pass when
`INTFER_DPAS_PREQ=1`, and adds **no host wait**.

**Why this is safe, precisely.** The hoisted values are *exact int32 sums of
int8 codes* (`|sum| <= 32*128 = 4096`, nowhere near overflow). Integer addition
is exact and associative, so moving the sum out of the tile loop cannot change
a single bit — there is no rounding-order exposure, unlike the FP32 folds
elsewhere in this file. The DPAS math, the scales and the accumulation order
are all untouched. This is a **work hoist, not a numerics change**.

### It is not a vacuous gate — measured
Two independent mutations, each reverted:
1. `fold_stride < 2*nOp` guard weakened back to `< nOp` → probe **rc=1**
   (negative case caught it: "declined but wrote 509 slots").
2. `dst[nOp + o] = sf` corrupted to `dst[o] = sf` → probe **rc=1** with the
   value comparison firing immediately on M=1.

### The bug this probe caught during development (read this before touching the layout)
My first version documented the row stride as `>= nOp`. That is **wrong: it
must be `>= 2*nOp`**, because each row owns `2*nOp` ints (`[S0][Sfull]`), so a
shorter stride lets row *m*'s Sfull block **overwrite row m+1's S0 block**.
This is **silent at M=1** (only row 0 exists) and only bites when the
grow-only workspace stride is smaller than the call's `2*nOp` — i.e. when a
smaller-K GEMM follows a larger one. The first run of the probe failed exactly
there (`M=8 big-K`: `S0` always right, `Sfull` garbage). Keep the `2*nOp`
guard in the kernel *and* in the engine; do not "simplify" either away.

### AUDIT #12: the SAME rule was NOT applied at the reader (read this before editing the layout again)

The `2*nOp` rule above was enforced **only in the writer**
(`quant_gemm_dpas48_rowfold`). Both **readers** resolved the row stride
independently and got it **wrong**:

```c
const uint32_t fold_stride = (p.fold_stride == 0) ? nOp : p.fold_stride;
```

`nOp`, not `2*nOp` — in `quant_gemm_dpas48` **and** again, verbatim, in
`quant_gemm_dpas4_row`. The header even *documented the bug as the contract*:
`uint32_t fold_stride = 0;  // 0 => nOp`. So the public API actively invited
any caller to write `fold_usm = buf;` and leave the stride at its default.

**Why it was not caught, and why it was dangerous.** Two reasons, and the
second is the interesting one:

1. *No gate could reach it.* The probe gated the **writer**'s output values.
   The engine always sets `fold_usm` **and** `fold_stride` together
   (`engine.cpp`: `fold_stride = 2 * ws48_[d].nOp`), so the four
   `test_gpu_optin.sh` FOLD arms — which do exercise M>1 and the row stride —
   are **structurally incapable** of hitting the `0` default. A path nothing
   reaches is a path nothing can break.

2. *The two halves mask each other.* This is why it survived the feature's own
   two mutations. The wrong default is **harmless while the reader validates**,
   and missing validation is **harmless while the default is right**. Data is
   only corrupted when **both** are wrong at once. Either bug alone looks fine.
   (Same species as the GA64 reciprocal and the AUDIT #4 "1 of M rows"
   findings: a rule fixed at one site and merely assumed at another.)

Fix — one shared rule, three call sites, fail-closed
(`include/intfer/gemm/quant_gemm.hpp`): `fold_row_stride()` resolves
`0 => 2*nOp`; `fold_readable()` additionally refuses any buffer whose stride
does not clear `2*nOp`, returning `nullptr` so the kernel falls back to the
**inline** fold — bit-identical to the pre-FOLD path, just without the hoist.
The writer and both readers now consume the same two functions.

Coverage added to the same probe (both mutation-proven, see §3):

- **contract** — 80 `(nOp, stride)` pairs; the reader must accept exactly the
  strides the writer accepts, resolving them identically. Expectations are an
  *independent* restatement of the writer's rule, so the check cannot pass by
  sharing code with the thing it checks.
- **device readback** — runs the real `quant_gemm_dpas48` against the inline
  fold in three stride regimes (correct / `0` default / too-small) and requires
  **bit-identical** FP16 outputs. The activations are built so `S0` and `Sfull`
  are deterministically distinct (lanes 0–15 `= +(m+1)`, lanes 16–31 `= -(m+1)`),
  so a mis-stride is caught **by construction**: with `nOp=1` a reader wrongly
  resolving `nOp` reads `fold_d[m+1]`, alternating Sfull/S0 between rows, and
  flips `S` for rows 1 and 3. Measured: **30/64 outputs corrupted**, not a
  probabilistic near-miss.

Measured mutation results (each reverted, tree re-verified green):

| mutation | contract | device readback |
|---|---|---|
| default `2*nOp` → `nOp` (the real bug) | **FAIL** (80 pairs) | pass — *masked* by validation |
| `fold_readable` returns `usm` unchecked | **FAIL** | pass — *masked* by the correct default |
| **both** (the historical state) | **FAIL** | **FAIL** 30/64 outputs |

The readback alone would have missed each single-half bug. That is the point of
keeping both checks: they fail on different halves of one defect.

## 4. What I already measured (load-insensitive counters only)

0.8B, `--tp 1`, box load 2-3 — **`total_kernel_us` is device-side event time,
not wall time**, and these are the numbers the report is allowed to quote:

| arm | shape | `total_kernel_us` | launches |
|---|---|---|---|
| `DPAS48` | decode n=8, M=1 | 88028.5 | 2232 |
| `DPAS48+FOLD` | decode n=8, M=1 | 86590.3 (**-1.6%**) | 2736 (**+504**) |
| `DPAS48` | prefill chunk128 | 43533.5 | 1116 |
| `DPAS48+FOLD` | prefill chunk128 | 42795.0 (**-1.7%**) | 1368 (**+252**) |

Read this honestly: the fold **costs one extra launch per DPAS GEMM call**
(+504 over 8 tokens, +252 over the prefill chunk) and buys a small device-side
kernel-time reduction on 0.8B. 0.8B is the *weak* case for this change: its N is
small, so there are few 16-N tiles to amortize the saved fold against, and the
added launch is pure overhead. **27B wide-N is where this is supposed to pay**,
and I cannot measure it here (one GPU; 27B needs `--tp 2`).

## 5. Expected direction and decision rule

- Device kernel time at fixed M,N,K: **down** (less replicated fold work).
- Launch count: **up**, one extra kernel per DPAS GEMM call. On 27B a GEMM is
  large enough that a tiny fold kernel should be cheap next to it, but that is
  a hypothesis, not a measurement.
- Wall time: unknown. The submit/launch tax is this project's dominant decode
  cost, and an extra launch per GEMM pushes the wrong way. Only you can settle
  it.

**Command** (precondition: both GPUs enumerate; see the backlog PRECONDITION):

```bash
BIN="${INTFER_BUILD_DIR:-build}/examples/intfer_cli/intfer_cli"
M=/var/home/fra/data/models/intfer/Qwen3.8-27B-int2.intifer
TOK="--tokenizer-py scripts/bpe_tokenize.py --detok-py scripts/bpe_detokenize.py"
export LD_LIBRARY_PATH=/opt/intel/oneapi/umf/1.1/lib:${LD_LIBRARY_PATH:-}

for r in 1 2 3; do
  echo "== round $r load1=$(awk '{print $1}' /proc/loadavg) =="
  for arm in "DPAS48" "FOLD"; do
    case $arm in
      DPAS48) unset INTFER_DPAS48_FOLD ;;
      FOLD)   export INTFER_DPAS48_FOLD=1 ;;
    esac
    INTFER_DPAS48=1 $BIN --gpu --tp 2 -m $M -p "The capital of France is" \
      -n 64 --no-stream $TOK 2>&1 | grep -aE "tokens in|decode:"
  done
done
```

**Decision rule**
- **WIN** — `FOLD` beats `DPAS48` by >3% decode **and** prefill at 27B, 3+
  interleaved rounds, `load1 < 2` each round. Only then is it worth combining
  with E1 (`INTFER_DPAS_PREQ`) and re-examining whether DPAS48 as a whole can
  ever be promoted off default-OFF.
- **NEUTRAL** — within ±3%. Expected if the launch tax eats the fold saving.
  Report it; it is still useful data (it bounds how much the replication cost).
- **KILL** — any decode regression, or `total_kernel_us` up. Keep default-OFF
  and add a row to the closed table in the backlog report.

**Correctness invariant you must re-check before believing any timing:**
`DPAS48+FOLD == DPAS48` byte-identical. If the ids differ, stop — that is a real
regression, not noise. (`base` vs `DPAS48` is *expected* to differ; DPAS48
changes activation numerics.)
