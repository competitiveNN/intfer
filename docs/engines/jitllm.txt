## 1. There is no SYCL/Xe backend -- the load-bearing fact, verified three ways

The claim that matters for an intfer survey is not "jitllm is not SYCL" but "jitllm has no kernel that could reach an Arc B580's matrix engines". Verified by three independent probes of the clone, not by one grep:

1. The backend list is jit/gpu/{cuda,vulkan,metal,hip,amdgpu,cpu} -- jit/gpu/backend/ holds upstream/jit/gpu/backend/alloccount.go, upstream/jit/gpu/backend/backend.go, cuda.go, grid.go, upstream/jit/gpu/backend/hip.go, upstream/jit/gpu/backend/identity.go, upstream/jit/gpu/backend/metal.go, upstream/jit/gpu/backend/owned.go, upstream/jit/gpu/backend/resources.go, upstream/jit/gpu/backend/tiles.go, upstream/jit/gpu/backend/tid_linux.go, upstream/jit/gpu/backend/tid_other.go, vulkan.go (besides its _test.go files), and jit/gpu/ holds amdgpu/, backend/, cuda/, ffi/, hip/, ir/, kernels/, lowertest/, metal/, msl/, ptx/, spirv/, tier/, vulkan/. There is no sycl/ or level_zero/ directory.
2. The upstream clone's README badge row is CUDA supported / Vulkan supported / Metal on Apple Silicon / ROCm untested / CPU x86 and Arm -- i.e. Intel is NOT a listed target at all.
3. The ONLY case-insensitive sycl hit in the whole tree is upstream/docs/engineering-history/scheduling-and-measurement.md:602, a parenthetical about which host packages Ubuntu gets ("ubuntu gets vulkan, rocm, sycl and openvino; CUDA is Windows-only"). That is a package-installation note, not a kernel.

The precise "Intel" hits elsewhere are all false positives for our purpose: upstream/jit/gpu/ir/ir.go:119 ("an Intel integrated GPU reports 32 and runs"), upstream/jit/gpu/kernels/divrn.go:8 ("NVIDIA's and Intel's Vulkan drivers return another last bit"), upstream/jit/gpu/vulkan/run.go:408 and upstream/jit/gpu/spirv/lower.go:279 (the 65535 Vulkan workgroup ceiling on an Intel iGPU), upstream/jit/gpu/vulkan/subgroup.go:8,23 (Intel iGPU subgroup sizes), upstream/jit/gpu/metal/metal_darwin.go:318 (an Intel Mac), and upstream/common/hardware/lines.go (CPU-model-string parsing). NONE is an Arc/dGPU matrix-engine path. This is the intfer/docs/audit-log-tooling.md failure-mode #35 shape handled correctly: the absence claim is triangulated across a directory listing, a documented target list, and an exhaustive grep, rather than resting on one pattern.

## 2. What IS transferable: host-side scheduling, and one design rule

jitllm's genuinely interesting engineering is HOST-SIDE and vendor-neutral: one kernel IR lowered to SPIR-V per backend (jit/gpu/spirv/), per-shader subgroup-width QUERY rather than a hardcoded width (upstream/jit/gpu/vulkan/subgroup.go:8-23), a paged KV history with explicit page faults (upstream/engine/model/kvpage.go:22), a host-resident packed-weight arena (upstream/jit/gpu/kernels/arena.go:9-24), and a JIT/trial instrument that picks kernels per device (upstream/jit/gpu/backend/backend.go:43-49).

intfer already ships the launch-geometry knob family (INTFER_DECODE1_WG, INTFER_XMX_WG, INTFER_LA_CONV_PREP_WG, INTFER_DPAS48_WG, INTFER_TILE_SCHED -- verified by fresh grep of intfer/src + include/), with intfer/scripts/knob_sweep.sh as the product harness. So the TECHNIQUE is already present. The one thing jitllm does that intfer does NOT is ask the device: intfer/src/gemm/quant_gemm.cpp:150 declares `constexpr int kThr = 16` and :484 reads `int nWG = kThr`, so the width is operator-set rather than device-queried. On this box the sub-group size is 16, so the hardcode is correct HERE and wrong in general -- a portability gap, recorded as a gap and NOT as a port candidate (a device query is a small change, not an upstream code port, and it changes no launch count).

## CONCLUSION

Nothing ports as code. jitllm has no SYCL/Level-Zero/oneAPI backend, so it offers no SYCL/Xe kernel and no XMX/DPAS path to adopt; its GGUF quant formats hit the DashQ INT2 weight-format wall, and its host-side paging adds a round trip rather than removing one. The one transferable insight is a DESIGN RULE intfer already mostly follows (per-device launch geometry, now shipped as the knob family) plus the narrower correction that intfer hardcodes the sub-group width instead of querying it.
