## 1. XMX DPAS flash attention -- NOT PORTABLE (fails the fusion test)

Upstream mechanism, read from the source: qwen35_xmx_attention (upstream/src/modeling/qwen3_5/kernels.hpp:761-905, its doc comment at :753-760) maps the whole attention block onto XMX -- Q[8,256] x K[16,256]^T per subgroup, then P[8,16] x V[16,256] per subgroup -- with online softmax over 16-key blocks and no materialised score matrix. The DPAS fragments are diff_dpas_v8s/v8i/v8f 8-wide, built by packing two bf16 lanes into a uint32 (upstream/src/modeling/qwen3_5/kernels.hpp:820-830).

Why it does not port: intfer's prefill attention runs on the HOST as FP32 dot/softmax/weighted-sum (intfer/examples/intfer_cli/main.cpp:4565 "softmax + V-weighted sum + copy to b_attn" and :5584 "every head's dot/softmax/weighted-sum keeps bit-identical"), and q/k/v are then re-read back into the host-visible KV cache. THE CORRECTED VERSION OF THIS CLAIM, because the first one was wrong: intfer is NOT free of device attention. intfer/src/attention/flash_attention.cpp ships TWO device FlashAttention kernels -- flash_attention_forward_f16 (FP16 Q/K/V, online-softmax tiling, kBr=kBc=64) and flash_attention_forward_int8_kv -- with the running max/sum at :71-72, the rescale at :106 and the K/V tiles staged through local_accessor at :47-48. What they are NOT is REACHABLE: intfer/src/engine/engine.cpp:33 is a bare #include with ZERO calls, the only call sites are intfer/examples/flash_attention_demo/main.cpp:117,130,174,203 and intfer/examples/qwen_forward_gpu/main.cpp:227, and intfer/examples/intfer_cli/main.cpp:4294 names the symbol in a COMMENT only. The header's own trace says the same (intfer/include/intfer/attention/flash_attention.hpp:9-25, "DEMO/REFERENCE-ONLY ... the engine that runs inference therefore has NO device softmax-attention kernel on any path"), though its two line pointers have since drifted (it names intfer/src/engine/engine.cpp:32 and intfer/examples/intfer_cli/main.cpp:3831; the current lines are 33 and 4294). So the blocker is REACHABILITY, not absence: there is no device attention on the 27B path for a DPAS attention kernel to accelerate, and intfer's own kernel would keep its round trips either way -- the XMX variant would replace EU/ALU arithmetic inside a kernel that already consumes device-resident Q/K/V, adding no round trip and removing none. The audit-log tooling failure-mode #35 lesson applies directly here and was MIS-APPLIED by this report's first draft: grepping for local_accessor / slm and concluding "no SLM" (zero hits) is wrong; the kernel uses group_local_memory_for_overwrite, an API that grep cannot see. The same lesson applied to the attention probe itself: online_softmax / online_attention / flash_attn finds nothing in intfer because intfer's symbols are flash_attention_forward_*. So the absence claim here is verified at the REACHABILITY level (the inference path calls no device attention kernel), not at a single-grep level.

## 2. SYCL command graphs -- NOT PORTABLE (counter-measured loss)

Upstream mechanism, read from the source: upstream/src/common/gpu/sycl_graph_session.hpp quant-neutral machinery over external/sycl/ext/oneapi/experimental/graph/command_graph.hpp, with an eager recording scope (DiffGraphScope) that makes q.wait() session-conditional and a counter cache (captures/replays/fallbacks/capacity_bypasses) exposed via diff_graph_capture_counts (upstream/src/common/gpu/sycl_graph_session.cpp:27-38).

Why it does not port: intfer already proved this exact idea a LOSS on this box (killed by the load-insensitive counters -- submit/waitblock/copy/readback/usm_write read as relative deltas, never tok/s). A graph removes submit overhead, not a host<->device round trip, and on this box submit savings land on an already-saturated queue. intfer's AGENTS.md records SYCL command graphs as an already counter-measured LOSS, DO NOT REVIVE. Fresh CASE-INSENSITIVE grep of intfer/src + include/ for command.graph returns FOUR hits, ALL COMMENTS (intfer/src/engine/engine.cpp:4 and intfer/include/intfer/engine.hpp:12,16,49 describe the intended capture), so no command-graph CODE is shipped -- and nothing should be revived. The earlier "ZERO hits" spelling grepped command_graph only and missed the hyphenated command-graph in those comments: failure mode #35 again.

## 3. NVFP4 / expert-parallel / layer splitting -- WALLS (weight format and P2P)

Upstream mechanism, read from the source: upstream/src/common/gpu/nvfp4.hpp's NVFP4 linear + matmul issues DPAS directly on 8-wide FP16×INT4 fragments; upstream/src/common/gpu/expert_parallel.hpp's Nvfp4Kernel {Default, Hybrid, Custom, GroupedDpas} picks an expert kernel and records that "a DPAS/XMX kernel was also explored and removed"; the upstream clone's README lists multi-GPU expert parallel and multi-GPU layer splitting.

Why neither ports: NVFP4 is not DashQ INT2, so it hits the weight-format wall -- re-laying out the whole 27B weight set is a re-quantisation, not a micro-optimisation (this is the same wall that closed mmvq and the vLLM Marlin int4 path, recorded in intfer's intfer/HISTORY.md). Expert-parallel and layer splitting both REQUIRE P2P, which intfer does not have (case-insensitive grep of intfer/src + include/ for allreduce / p2p / peer returns only COMMENTS saying "there is no P2P on this box": intfer/src/gemm/quant_gemm.cpp:2731, intfer/src/engine/engine.cpp:2124, intfer/src/engine/engine.cpp:2593, intfer/include/intfer/engine.hpp:197, intfer/include/intfer/engine.hpp:337, intfer/include/intfer/gemm/quant_gemm.hpp:249). Layer splitting is additionally documented as HARMFUL for the state-space (GDN) class the 27B belongs to (intfer/docs/FORK_B580_SUMMARY.md sec.18).
